# outliers-sim: Decisions

Working name. Separate from the `outliers` workspace.

## Decided (2026-10-09)

| Topic | Decision |
|---|---|
| Users | Both coders and non-coders. Plain-text models are the source of truth; a GUI edits them. |
| Project type | Open source |
| MVP focus | Text models, git and CI: diffable models, headless runs, automated tests, reproducible seeds |
| Engine | Rust |
| Front end | Godot (visual editor and animation) |
| Model format | Declarative YAML plus a small expression language for logic |
| Godot in v1 | Viewer/animator only: reads the model and an event log, plays it back, no editing |
| License | MIT / Apache-2.0 (dual, Rust convention) |
| First example domain | Manufacturing (job shop, buffers, breakdowns) |

## Why Rust for the engine (not C++ inside Godot)

- Speed isn't the reason. Rust and C++ run at about the same speed (both compile to native code; Rust uses the LLVM backend, like Clang). DES speed depends on the event list structure, avoiding allocation for each event, data layout, the random number generator and parallel replications, not on the language. GDScript would be the slow option.
- The reason is that the engine has to stand alone. A Godot module or a C++ GDExtension built on Godot's types would tie the engine to Godot, which contradicts the headless, CI-first MVP.
- Rust's advantages over a standalone C++ library: Cargo; ready-made libraries (`rand`/`rand_distr`, `serde` + `toml`/`serde_yaml`, `rayon`, `arrow`/`parquet`); memory safety for outside contributors; PyO3 and WASM available later.

## Why Godot for the v1 viewer (not Bevy or egui)

- The event log is the only connection, so the front end can be replaced later without touching the engine.
- Godot's scene editor saves the most effort in the 3D work (factory layouts, cameras). Bevy has no editor.
- The user already knows Godot. Bevy has had breaking changes every few months.
- Reconsider all-Rust (Bevy/egui + engine compiled to WASM) if sharing in a browser becomes a priority. Godot's web export is harder when the project uses Rust extensions.
- Expect a separate view for results (queue lengths over time, utilization, confidence intervals), because game engines are weak at charts. Options: egui, a web page, or HTML reports from the command-line tool. It may be the first front end built, since it fits the headless MVP.

## Implications

- The Rust engine must run fully headless, with no Godot dependency. Godot is one client of the engine, not part of it.
- The text model format is the central decision. It's what gets diffed, reviewed, tested and generated by AI, and what the Godot editor has to read and write without loss.
- Godot ↔ Rust options: link the engine in-process with gdext (godot-rust), or run it as a separate process that streams events. The MVP focus (headless, CI) points toward a CLI binary first, with Godot added later.

- With Godot as a viewer only, the boundary between engine and front end is an event log file. That keeps them fully decoupled: Godot never links the engine in v1.
- The expression language decides how far the declarative format can go. Keep it small (arithmetic, distributions, attribute access, conditions). When a model outgrows it, that's the signal to add a scripting escape hatch, not to grow the expression language into a full language.

## YAML guardrails

- Use a YAML 1.2 parser, so `no`/`yes`/`on` stay strings (the "Norway problem").
- `serde_yaml` has been unmaintained since 2024. Pick the parser crate when development starts, and check how well each candidate is maintained at that point.
- Publish a JSON Schema for the model format, so editors with yaml-language-server (e.g. VS Code) give autocomplete and validation for free.
- Validate strictly: reject unknown keys and give error messages with line and column numbers.
- Keep durations and units as quoted strings (`"8 h"`, `"triangular(1 min, 3 min, 6 min)"`), so YAML never guesses their type.
- Decide whether anchors and aliases (`&`, `*`) are allowed. They're handy for reuse, but complicate a future GUI editor that has to save the file back without changing it unexpectedly.

## Units and time

- Units exist only at the edges. Model files carry units, and a model may declare default units (`units: { time: min, length: m }`) so plain numbers are allowed. The loader checks units and converts everything to standard units once, at load time. The engine core never sees a unit: time is in seconds and length in meters. Choosing display units is up to the front ends and reports.
- The engine stores time as 64-bit integer microseconds, not floating point. Simultaneous events are then exactly simultaneous, tie-breaking follows an explicit, documented rule, and results are identical on every platform. Values drawn from distributions are rounded to the nearest µs.

## Format conventions (from examples/conveyor-line.yaml)

- Objects are grouped by type (`sources`, `servers`, `conveyors`, `sinks`). Names are unique across all types.
- Conveyors define how objects connect, through their `from` and `to` fields.
- Every quantity carries a unit (`"0.5 m/s"`, `"8 h"`), unless the model sets default units. Distributions are expression strings.
- Layout lives in a separate `*.layout.yaml` file that only the viewer reads, so moving things around never changes the logic.
- Server states: idle (starved), busy, blocked, failed. Blocking happens after service: a finished part stays on the server until the next conveyor has room.

## Loader (implemented 2026-10-09)

- YAML parser: `serde-saphyr`. Actively maintained, YAML 1.2, errors with line and column, and `Spanned<T>` so validation errors can point at the exact value. Options: `strict_booleans` (only `true`/`false` are booleans); duplicate keys are errors (the default).
- Two kinds of errors. Syntax errors (bad YAML, unknown key, wrong type, unknown option value) stop at the first one. Validation errors (unknown names, units, distributions, connections) are all collected and reported in file order. Follow-on errors caused by a misspelled conveyor endpoint are suppressed.
- Objects keep file order (no hash maps), so indices, and therefore results, are deterministic.
- Names: letters, digits, `_` and `-`, starting with a letter or `_`. They end up in event logs, CSV columns and command lines.
- Units: time `ms s min h d`; length `mm cm m km`; speed `<length>/<time>`. A number and its unit must be separated by a space (`12 m`, not `12m`).
- Distributions: `constant` (or a bare time), `exponential(mean)`, `uniform(min, max)`, `triangular(min, mode, max)`, `lognormal(mean, sd)`, where the lognormal parameters are the mean and sd of the distribution itself. Arguments can be positional or named. No `normal`, since it can go negative; `weibull`/`gamma` are likely next for failures.
- v1 topology limits: each source has exactly one outgoing conveyor, each server exactly one incoming and one outgoing, and sinks at least one incoming. Every server must be reachable from a source. Routing and merging come later, and they'll need explicit tie-breaking rules.
- Outputs defaults: `event_log: none`; `summary`: all items.

## Engine core (implemented 2026-10-09)

- **Random numbers are our own code, not a crate's:** xoshiro256++ plus our own samplers (inverse transform where a closed form exists, Box-Muller for the lognormal). A seed gives the same numbers forever, whatever version of `rand` is current.
- **One stream per random input,** derived from (seed, replication, name), e.g. `server/lathe/process` or `server/lathe/failure/breakdown/uptime`. Adding or changing one input doesn't shift the random numbers of the others (common random numbers across scenarios). Renaming an object does change its stream.
- **Tie-breaking:** events at the same time run in the order they were scheduled. Events at exactly the end of the run aren't processed.
- **Sources:** the first arrival is at t = 0. A waiting source holds the part and starts the next interarrival only once the part gets on the conveyor.
- **Accumulating conveyors:** parts are points moving at the belt speed. The head stops at the end, and followers stop one spacing behind the part ahead. A part can get on when the conveyor holds fewer than `floor(length / spacing)` parts and the last part is at least one spacing from the entrance. When the head leaves, all stopped parts move again at once (no restart delay). Positions are computed only when needed, so no events are spent on movement.
- **Servers:** a server takes a part when it's up and has a free slot. A finished part blocks its slot until the outgoing conveyor has room, and blocked parts leave in the order they finished. State shares are fractions of capacity × time, and they add up to 1. While the server is down, its whole capacity counts as failed.
- **Failures:** clocks only run while the server is up; `busy_time` clocks also need at least one slot processing. A down server does nothing: it doesn't process, take parts or release blocked parts. `restart` repeats the part's original process time instead of drawing a new one.
- **Statistics:** time averages are exact (integer value × integer µs) and updated after every event. The warm-up resets everything. Time in system counts parts that exit after the warm-up, including parts created before it.
- **Trace:** the engine emits per-part events (created, entered conveyor, reached end, started/finished process, exited, lost) and failure/repair events through an `Observer`. Event logs and the viewer are built on it.
- **Performance (first measurement):** 30 replications × 128 h of the conveyor-line example in 0.36 s on one thread, release build, with the full trace kept in memory. That's about 7 M trace events/s.

## Verification against queueing theory (implemented 2026-10-09)

`crates/engine/tests/queueing.rs` runs models with exact analytical answers on every `cargo test`, and so in CI. Conveyors are made practically invisible: 1 ms transit, room for 10,000 parts, 0.1 µs to close up a queue.

| Model | Exact answer from | Checks |
|---|---|---|
| M/M/1, ρ = 0.7 | 1 / (μ − λ) | time in system, utilization |
| M/M/3 | Erlang C | time in system, utilization |
| M/D/1, M/G/1 triangular, M/G/1 lognormal | Pollaczek-Khinchine | time in system |
| M/G/1 with exponential busy-time failures, preemptive resume | P-K on the completion time C = S + repairs during S | time in system, failed share, busy share |
| Two M/M/1 in series | Burke's theorem | time in system |
| M/M/1/5 with `when_blocked: drop` | finite-capacity formulas + PASTA | share of arrivals lost, time in system |

- **Pass rule:** 20 replications × 1000 h after a 50 h warm-up. The exact value must be within 4 standard errors of the estimate, and the relative standard error must be ≤ 2% (≤ 1% for utilization), so a pass actually means something. Seeds are fixed, so tests never flake.
- **Bias check:** with the default seed, all estimates were slightly low (between −0.4 and −1.7 SE). They share the arrival stream through common random numbers, so they move together. Seeds 7, 12345 and 99 flip the signs (seed 12345 is mostly positive), so there's no sign of bias.
- The engine is built with `opt-level = 3` even in debug builds (`[profile.dev.package.outliers-sim-engine]`), so the whole test suite runs in about 5 s.

## `run` and result files (implemented 2026-10-09)

- Replications run in parallel on all cores (`--threads` to limit), with a work queue and no extra crate. Results are identical whatever the thread count; a test compares the output files byte for byte.
- Every measure is reported as mean ± 95% Student-t confidence interval across replications, plus min and max. The t quantiles are computed in the engine (log-gamma + incomplete beta), with no stats crate. With 1 replication the CI shows "n/a" and a warning.
- Output goes to `results/<model name>/` by default (`--output-dir` to change; gitignored):
  - `summary.json`: one entry per measure with n, mean, half-width, sd, min and max, in standard units with an explicit `unit` field (`s`, `fraction`, `parts`, `parts/h`, `count`).
  - `replications.csv`: long format, one row per replication × measure. Raw values for spreadsheets, pandas or R.
  - `events.jsonl`: only when the model sets `outputs.event_log: jsonl`, and for one replication (`--log-replication`, default 1). The whole run is included, warm-up too.
- **Event log format, decided: JSON Lines** (`outliers-sim-events/0.1`). The first line is a header with the model structure the viewer needs (conveyor ends, length, speed, spacing and capacity; server capacity and failure names). Then one event per line, with `t` in seconds written exactly to the µs, and objects referred to by name. Size: about 6 MB / 88k lines for 128 h of the conveyor line. Parquet can come later if size becomes a problem.
- Display units are chosen per measure by the table (fractions → %, durations → s/min/h by magnitude). Files always use standard units.

## HTML report (implemented 2026-10-09)

- `run` always writes `report.html`: one self-contained file. The template (`crates/cli/src/report.html`) is compiled into the binary, and the results are embedded as JSON and drawn with plain JS and SVG. No CDN and no network: it opens offline, can be attached to an email, and still works in 10 years. It contains no timestamp, so the same model and seed give a byte-identical report (tested).
- Sections:
  - headline tiles (throughput, time in system, source blocked/lost), each with its CI and range;
  - stacked bars of server states;
  - conveyor fill meters (mean parts vs capacity, % of time full);
  - "variation across replications" dot plots (one dot per replication, mean line and CI band), shown on purpose so a single run can't pass as an answer;
  - the full table.
- Every chart has hover/keyboard tooltips with CIs; values are also in the table, so nothing depends on hovering.
- Colors follow the dataviz reference palette. Server states use its first three categorical slots (busy blue, blocked orange, failed aqua), which are published as validated all-pairs for colour-vision deficiency in both modes, and idle is a neutral gray. The palette validator wasn't run locally (no Node.js); rerun it if the colors change. Dark mode uses its own color steps, not an inverted light theme. Labels inside bars use ink or white, whichever has more contrast against the fill.

## Viewer (implemented 2026-10-09)

- **Folder:** `viewer/`, a Godot 4.7 project in GDScript.
- **Renderer:** Compatibility, so the same project runs on desktop, Android (Godot Editor app) and, later, web exports.
- **What it opens:** a results folder. It reads `events.jsonl` and, if present, `layout.json`.
- **Layouts:** the viewer never parses YAML. `run` checks `<model>.layout.yaml` (or `--layout`) against the model in Rust, with located errors, and writes `layout.json` in meters, Y up. `validate` checks the layout too. Every source, server, sink and conveyor must be placed, and unknown names are errors. A drawn conveyor whose length differs from the model's by more than 1% gives a warning, and the viewer stretches its animation to fit.
- **No layout file:** objects are placed in a row along each source's chain.
- **Replay:** `viewer/scripts/replay.gd` rebuilds the state at any time from the log. It uses the engine's conveyor rules exactly (lazy positions, rebase when the head leaves), so the animation shows what the engine computed, not an approximation. Seeking backward replays from the start (88k events: fast enough). Server color follows the report's palette, by precedence failed > blocked > busy > idle.
- **Controls:**
  - play/pause and speed from 1× to 3600× (keys: space, `,` and `.`);
  - a timeline you can drag;
  - mouse: drag to orbit, right-drag to pan, wheel to zoom;
  - touch: one finger orbits, pinch zooms and pans.
- **Tests:** `viewer/tests/run_all.sh` simulates the fixtures with the current CLI, then runs headless:
  - the replay test, with exact positions on a deterministic model and an accumulated, blocked line on a two-server model;
  - the main scene for 300 frames, with and without a layout.

  A deliberately broken accumulation rule makes the replay test fail. The rendered look can't be checked here: there's no display on the server.

- **Demo:** `viewer/demo/` holds replication 1 of the conveyor-line example (`events.jsonl.gz`, about 650 KB, plus `layout.json`). The viewer opens it when started without arguments, e.g. from the Android Godot Editor, where the Rust CLI can't run. `make_demo.sh` regenerates it byte for byte (`gzip -n`), and `run_all.sh` fails if the committed demo doesn't match the current CLI. The viewer reads `.jsonl.gz` as well as `.jsonl`.
- **Repository:** `GusFurtado/outliers-sim` on GitHub, private for now (2026-10-09), so the tablet can pull the viewer. It's meant to go public later.
