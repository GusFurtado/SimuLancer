# outliers-sim: Decisions

Working name. Separate from the `outliers` workspace.

## Decided (2026-10-09)

| Topic | Decision |
|---|---|
| Users | Both coders and non-coders. Plain-text models are the source of truth; a GUI edits them. |
| Project type | Open source |
| MVP focus | Text models, git and CI: diffable models, headless runs, automated tests, reproducible seeds |
| Engine | Rust |
| Front end | Godot (visual editor and animation) |
| Model format | Declarative YAML plus a small expression language for logic |
| Godot in v1 | Viewer/animator only: reads the model and an event log, plays it back, no editing |
| License | MIT / Apache-2.0 (dual, Rust convention) |
| First example domain | Manufacturing (job shop, buffers, breakdowns) |

## Why Rust for the engine (not C++ inside Godot)

- Speed isn't the reason. Rust and C++ run at about the same speed (both compile to native code; Rust uses the LLVM backend, like Clang). DES speed depends on the event list structure, avoiding allocation for each event, data layout, the random number generator and parallel replications, not on the language. GDScript would be the slow option.
- The reason is that the engine has to stand alone. A Godot module or a C++ GDExtension built on Godot's types would tie the engine to Godot, which contradicts the headless, CI-first MVP.
- Rust's advantages over a standalone C++ library: Cargo; ready-made libraries (`rand`/`rand_distr`, `serde` + `toml`/`serde_yaml`, `rayon`, `arrow`/`parquet`); memory safety for outside contributors; PyO3 and WASM available later.

## Why Godot for the v1 viewer (not Bevy or egui)

- The event log is the only connection, so the front end can be replaced later without touching the engine.
- Godot's scene editor saves the most effort in the 3D work (factory layouts, cameras). Bevy has no editor.
- The user already knows Godot. Bevy has had breaking changes every few months.
- Reconsider all-Rust (Bevy/egui + engine compiled to WASM) if sharing in a browser becomes a priority. Godot's web export is harder when the project uses Rust extensions.
- Expect a separate view for results (queue lengths over time, utilization, confidence intervals), because game engines are weak at charts. Options: egui, a web page, or HTML reports from the command-line tool. It may be the first front end built, since it fits the headless MVP.

## Implications

- The Rust engine must run fully headless, with no Godot dependency. Godot is one client of the engine, not part of it.
- The text model format is the central decision. It's what gets diffed, reviewed, tested and generated by AI, and what the Godot editor has to read and write without loss.
- Godot ↔ Rust options: link the engine in-process with gdext (godot-rust), or run it as a separate process that streams events. The MVP focus (headless, CI) points toward a CLI binary first, with Godot added later.

- With Godot as a viewer only, the boundary between engine and front end is an event log file. That keeps them fully decoupled: Godot never links the engine in v1.
- The expression language decides how far the declarative format can go. Keep it small (arithmetic, distributions, attribute access, conditions). When a model outgrows it, that's the signal to add a scripting escape hatch, not to grow the expression language into a full language.

## YAML guardrails

- Use a YAML 1.2 parser, so `no`/`yes`/`on` stay strings (the "Norway problem").
- `serde_yaml` has been unmaintained since 2024. Pick the parser crate when development starts, and check how well each candidate is maintained at that point.
- Publish a JSON Schema for the model format, so editors with yaml-language-server (e.g. VS Code) give autocomplete and validation for free.
- Validate strictly: reject unknown keys and give error messages with line and column numbers.
- Keep durations and units as quoted strings (`"8 h"`, `"triangular(1 min, 3 min, 6 min)"`), so YAML never guesses their type.
- Decide whether anchors and aliases (`&`, `*`) are allowed. They're handy for reuse, but complicate a future GUI editor that has to save the file back without changing it unexpectedly.

## Units and time

- Units exist only at the edges. Model files carry units, and a model may declare default units (`units: { time: min, length: m }`) so plain numbers are allowed. The loader checks units and converts everything to standard units once, at load time. The engine core never sees a unit: time is in seconds and length in meters. Choosing display units is up to the front ends and reports.
- The engine stores time as 64-bit integer microseconds, not floating point. Simultaneous events are then exactly simultaneous, tie-breaking follows an explicit, documented rule, and results are identical on every platform. Values drawn from distributions are rounded to the nearest µs.

## Format conventions (from examples/conveyor-line.yaml)

- Objects are grouped by type (`sources`, `servers`, `conveyors`, `sinks`). Names are unique across all types.
- Conveyors define how objects connect, through their `from` and `to` fields.
- Every quantity carries a unit (`"0.5 m/s"`, `"8 h"`), unless the model sets default units. Distributions are expression strings.
- Layout lives in a separate `*.layout.yaml` file that only the viewer reads, so moving things around never changes the logic.
- Server states: idle (starved), busy, blocked, failed. Blocking happens after service: a finished part stays on the server until the next conveyor has room.

## Loader (implemented 2026-10-09)

- YAML parser: `serde-saphyr`. Actively maintained, YAML 1.2, errors with line and column, and `Spanned<T>` so validation errors can point at the exact value. Options: `strict_booleans` (only `true`/`false` are booleans); duplicate keys are errors (the default).
- Two kinds of errors. Syntax errors (bad YAML, unknown key, wrong type, unknown option value) stop at the first one. Validation errors (unknown names, units, distributions, connections) are all collected and reported in file order. Follow-on errors caused by a misspelled conveyor endpoint are suppressed.
- Objects keep file order (no hash maps), so indices, and therefore results, are deterministic.
- Names: letters, digits, `_` and `-`, starting with a letter or `_`. They end up in event logs, CSV columns and command lines.
- Units: time `ms s min h d`; length `mm cm m km`; speed `<length>/<time>`. A number and its unit must be separated by a space (`12 m`, not `12m`).
- Distributions:
  - `constant` (or a bare time)
  - `exponential(mean)`
  - `uniform(min, max)`
  - `triangular(min, mode, max)`
  - `lognormal(mean, sd)`, where the parameters are the mean and sd of the distribution itself
  - `weibull(shape, scale)`, added 2026-10-09
  - `gamma(shape, scale)`, added 2026-10-09

  Arguments can be positional or named. Shape parameters are plain numbers without units; every other argument is a time. There's no `normal`, since it can go negative.
- Weibull is the standard choice for failures that get more likely with age (shape > 1) or less likely (shape < 1); shape 1 is exponential. Gamma fits repair and process times with a mode above zero. Sampling:
  - Weibull: inverse transform, one number per draw.
  - Gamma: Marsaglia–Tsang rejection, which uses a varying number of draws. This doesn't hurt common random numbers: each input has its own stream, so its k-th sample is the same in both scenarios however many draws each sample took.

  Both are checked by moment tests (including shape < 1) and by M/G/1 queueing tests.
- Topology (since 2026-10-09, see "Routing and merging"): sources need at least one outgoing conveyor, servers at least one incoming and one outgoing, sinks at least one incoming. Every server must be reachable from a source, and every source and server must have a path to a sink (loops are fine as long as there's a way out).
- Outputs defaults: `event_log: none`; `summary`: all items.

## Engine core (implemented 2026-10-09)

- **Random numbers are our own code, not a crate's:** xoshiro256++ plus our own samplers (inverse transform where a closed form exists, Box-Muller for the lognormal). A seed gives the same numbers forever, whatever version of `rand` is current.
- **One stream per random input,** derived from (seed, replication, name), e.g. `server/lathe/process` or `server/lathe/failure/breakdown/uptime`. Adding or changing one input doesn't shift the random numbers of the others (common random numbers across scenarios). Renaming an object does change its stream.
- **Tie-breaking:** events at the same time run in the order they were scheduled. Events at exactly the end of the run aren't processed.
- **Sources:** the first arrival is at t = 0. A waiting source holds the part and starts the next interarrival only once the part gets on the conveyor.
- **Accumulating conveyors:** parts are points moving at the belt speed. The head stops at the end, and followers stop one spacing behind the part ahead. A part can get on when the conveyor holds fewer than `floor(length / spacing)` parts and the last part is at least one spacing from the entrance. When the head leaves, all stopped parts move again at once (no restart delay). Positions are computed only when needed, so no events are spent on movement.
- **Servers:** a server takes a part when it's up and has a free slot. A finished part blocks its slot until its outgoing conveyor has room. Each blocked part leaves as soon as its conveyor has room; parts waiting for the same conveyor leave in the order they finished. State shares are fractions of capacity × time, and they add up to 1. While the server is down, its whole capacity counts as failed.
- **Failures:** clocks only run while the server is up; `busy_time` clocks also need at least one slot processing. A down server does nothing: it doesn't process, take parts or release blocked parts. `restart` repeats the part's original process time instead of drawing a new one.
- **Statistics:** time averages are exact (integer value × integer µs) and updated after every event. The warm-up resets everything. Time in system counts parts that exit after the warm-up, including parts created before it.
- **Trace:** the engine emits per-part events (created, entered conveyor, reached end, started/finished process, exited, lost) and failure/repair events through an `Observer`. Event logs and the viewer are built on it.
- **Performance (first measurement):** 30 replications × 128 h of the conveyor-line example in 0.36 s on one thread, release build, with the full trace kept in memory. That's about 7 M trace events/s.

## Verification against queueing theory (implemented 2026-10-09)

`crates/engine/tests/queueing.rs` runs models with exact analytical answers on every `cargo test`, and so in CI. Conveyors are made practically invisible: 1 ms transit, room for 10,000 parts, 0.1 µs to close up a queue.

| Model | Exact answer from | Checks |
|---|---|---|
| M/M/1, ρ = 0.7 | 1 / (μ − λ) | time in system, utilization |
| M/M/3 | Erlang C | time in system, utilization |
| M/D/1, M/G/1 triangular, M/G/1 lognormal | Pollaczek-Khinchine | time in system |
| M/G/1 with exponential busy-time failures, preemptive resume | P-K on the completion time C = S + repairs during S | time in system, failed share, busy share |
| Two M/M/1 in series | Burke's theorem | time in system |
| M/M/1/5 with `when_blocked: drop` | finite-capacity formulas + PASTA | share of arrivals lost, time in system |

- **Pass rule:** 20 replications × 1000 h after a 50 h warm-up. The exact value must be within 4 standard errors of the estimate, and the relative standard error must be ≤ 2% (≤ 1% for utilization), so a pass actually means something. Seeds are fixed, so tests never flake.
- **Bias check:** with the default seed, all estimates were slightly low (between −0.4 and −1.7 SE). They share the arrival stream through common random numbers, so they move together. Seeds 7, 12345 and 99 flip the signs (seed 12345 is mostly positive), so there's no sign of bias.
- The engine is built with `opt-level = 3` even in debug builds (`[profile.dev.package.outliers-sim-engine]`), so the whole test suite runs in about 5 s.

## `run` and result files (implemented 2026-10-09)

- Replications run in parallel on all cores (`--threads` to limit), with a work queue and no extra crate. Results are identical whatever the thread count; a test compares the output files byte for byte.
- Every measure is reported as mean ± 95% Student-t confidence interval across replications, plus min and max. The t quantiles are computed in the engine (log-gamma + incomplete beta), with no stats crate. With 1 replication the CI shows "n/a" and a warning.
- Output goes to `results/<model name>/` by default (`--output-dir` to change; gitignored):
  - `summary.json`: one entry per measure with n, mean, half-width, sd, min and max, in standard units with an explicit `unit` field (`s`, `fraction`, `parts`, `parts/h`, `count`).
  - `replications.csv`: long format, one row per replication × measure. Raw values for spreadsheets, pandas or R.
  - `events.jsonl`: only when the model sets `outputs.event_log: jsonl`, and for one replication (`--log-replication`, default 1). The whole run is included, warm-up too.
- **Event log format, decided: JSON Lines** (`outliers-sim-events/0.1`). The first line is a header with the model structure the viewer needs (conveyor ends, length, speed, spacing and capacity; server capacity and failure names). Then one event per line, with `t` in seconds written exactly to the µs, and objects referred to by name. Size: about 6 MB / 88k lines for 128 h of the conveyor line. Parquet can come later if size becomes a problem.
- Display units are chosen per measure by the table (fractions → %, durations → s/min/h by magnitude). Files always use standard units.

## HTML report (implemented 2026-10-09)

- `run` always writes `report.html`: one self-contained file. The template (`crates/cli/src/report.html`) is compiled into the binary, and the results are embedded as JSON and drawn with plain JS and SVG. No CDN and no network: it opens offline, can be attached to an email, and still works in 10 years. It contains no timestamp, so the same model and seed give a byte-identical report (tested).
- Sections:
  - headline tiles (throughput, time in system, source blocked/lost), each with its CI and range;
  - stacked bars of server states;
  - conveyor fill meters (mean parts vs capacity, % of time full);
  - "variation across replications" dot plots (one dot per replication, mean line and CI band), shown on purpose so a single run can't pass as an answer;
  - the full table.
- Every chart has hover/keyboard tooltips with CIs; values are also in the table, so nothing depends on hovering.
- Colors follow the dataviz reference palette. Server states use its first three categorical slots (busy blue, blocked orange, failed aqua), which are published as validated all-pairs for colour-vision deficiency in both modes, and idle is a neutral gray. The palette validator wasn't run locally (no Node.js); rerun it if the colors change. Dark mode uses its own color steps, not an inverted light theme. Labels inside bars use ink or white, whichever has more contrast against the fill.

## Viewer (implemented 2026-10-09)

- **Folder:** `viewer/`, a Godot 4.7 project in GDScript.
- **Renderer:** Compatibility, so the same project runs on desktop, Android (Godot Editor app) and, later, web exports.
- **What it opens:** a results folder. It reads `events.jsonl` and, if present, `layout.json`.
- **Layouts:** the viewer never parses YAML. `run` checks `<model>.layout.yaml` (or `--layout`) against the model in Rust, with located errors, and writes `layout.json` in meters, Y up. `validate` checks the layout too. Every source, server, sink and conveyor must be placed, and unknown names are errors. A drawn conveyor whose length differs from the model's by more than 1% gives a warning, and the viewer stretches its animation to fit.
- **No layout file:** objects are placed in a row along each source's chain.
- **Replay:** `viewer/scripts/replay.gd` rebuilds the state at any time from the log. It uses the engine's conveyor rules exactly (lazy positions, rebase when the head leaves), so the animation shows what the engine computed, not an approximation. Seeking backward replays from the start (88k events: fast enough). Server color follows the report's palette, by precedence failed > blocked > busy > idle.
- **Controls:**
  - play/pause and speed from 1× to 3600× (keys: space, `,` and `.`);
  - a timeline you can drag;
  - mouse: drag to orbit, right-drag to pan, wheel to zoom;
  - touch: one finger orbits, pinch zooms and pans.
- **Tests:** `viewer/tests/run_all.sh` simulates the fixtures with the current CLI, then runs headless:
  - the replay test, with exact positions on a deterministic model and an accumulated, blocked line on a two-server model;
  - the main scene for 300 frames, with and without a layout.

  A deliberately broken accumulation rule makes the replay test fail. The rendered look can't be checked here: there's no display on the server.

- **Demo:** `viewer/demo/` holds replication 1 of the conveyor-line example (`events.jsonl.gz`, about 650 KB, plus `layout.json`). The viewer opens it when started without arguments, e.g. from the Android Godot Editor, where the Rust CLI can't run. `make_demo.sh` regenerates it byte for byte (`gzip -n`), and `run_all.sh` fails if the committed demo doesn't match the current CLI. The viewer reads `.jsonl.gz` as well as `.jsonl`.
- **Repository:** `GusFurtado/outliers-sim` on GitHub, private for now (2026-10-09), so the tablet can pull the viewer. It's meant to go public later.

## Routing and merging (implemented 2026-10-09)

Splitting and merging are where proprietary tools hide their tie-breaking. Here the rule is required whenever there's a choice: a source or server with two or more outgoing conveyors needs `output: { rule: ... }`, and a server with two or more incoming conveyors needs `input: { rule: ... }`. Leaving it out is an error that lists the conveyors and the options.

**Output rules.** The conveyor is chosen when the part is ready to leave: when it's created, or when it finishes processing.

| Rule | Behavior |
|---|---|
| `probability` | Draws from the object's own `routing` stream (so scenario comparisons still pair up), using `weights` per conveyor. The weights must name exactly the outgoing conveyors, be > 0, and add up to 1 (± 1e-6). The part waits for the chosen conveyor. |
| `round_robin` | Outputs in strict rotation. The part waits for its turn's conveyor. |
| `first_available` | The first output in file order with room. |
| `shortest_queue` | The output holding the fewest parts, among those with room; ties go to the one listed first. |

For `first_available` and `shortest_queue`, if no output has room, the part takes whichever conveyor gets room first.

**Input rules.**

| Rule | Behavior |
|---|---|
| `first_come` | The part that reached the end of its conveyor first. Ties go to the input listed first. |
| `priority` | `order: [...]` lists every incoming conveyor exactly once, highest priority first. |
| `round_robin` | In turn, skipping inputs with nothing waiting. |

- **Simultaneous arrivals:** for servers with several inputs, the choice happens in a `Pull` event at the current time. Every arrival already due at that instant is considered, so the rule decides, not the order events happen to run in. A test checks a `first_come` tie, and a deliberate mutation that skips the deferral makes it fail. Single-input servers decide at once, as before.
- **Sinks** take every part immediately and need no rule.
- **Existing models are unaffected:** the conveyor-line example's event log is byte-identical before and after this change (checked by the viewer demo freshness test).
- **Loops** (rework, retest on the same server) are allowed. Validation requires that every source and server has a path to a sink.
- **Throughput per conveyor** (parts/h) is reported for every conveyor, so splits are visible in the summary.
- **Validation tests:**
  - every rule, plus the simultaneous-arrival cases;
  - a probability split's shares: 0.3 within 0.004 over 360k parts;
  - queueing theory: a Poisson split into two M/M/1 queues, and an M/M/1 with Bernoulli feedback (p = 0.2; T = 1/((1 − p)(μ − λ/(1 − p))) = 3 min), checked across several seeds for bias;
  - the viewer replays a model with a priority merge, a three-input first-come merge, rework and a self-loop, and every part the log says is in the system is visible.
- **Example:** `examples/two-cells.yaml` (with a layout): `shortest_queue` into two mills, a `first_come` merge at inspection, 10% rework to mill A with `priority` over new parts. With `first_available` instead, mean time in system was 24.6 min instead of 9.1 min. The rule matters, and now it's one visible line in the model.
- **Viewer auto layout:** objects without a layout file go in columns by distance from the sources. Backward conveyors and self-loops are drawn around the top, each in its own lane.

## Scenario comparison (implemented 2026-10-09)

- `outliers-sim compare base.yaml scenario.yaml` runs both models with the same seed and replication numbers. Random streams come from (seed, replication, object name), so wherever the two models share names they see the same arrivals, process times and failures (common random numbers).
- **Paired differences:** for each measure in both models (matched by object type, object and measure name), the difference is computed per replication (scenario − base). The report shows its mean, a 95% t confidence interval and a verdict: *higher* or *lower* when the CI excludes zero, otherwise *no clear difference*; *identical* when every pair is equal.
- **Precision of pairing:** `comparison.json` also stores the Welch CI an unpaired comparison would have had. The CLI prints the median gain; for the c2 buffer example, pairing makes the CIs 5.6× narrower. A model compared with itself gives exactly zero differences (tested).
- **Experiment settings must match:** seed, replications, warm-up and run length, or the comparison is refused with a message showing both. `--replications` overrides both.
- **Renaming breaks pairing:** an object renamed between the two models gets different random numbers and isn't compared. Scenarios are full copies of the model for now (e.g. `examples/conveyor-line-longer-c2.yaml`); scenario files that only list changes are a possible next step.
- **Routing rules compared** (`examples/two-cells-first-available.yaml` and `two-cells-round-robin.yaml`, which differ from `two-cells.yaml` only in the source's `output` rule; 30 paired replications):

  | vs `shortest_queue` | time in system | throughput | notes |
  |---|---|---|---|
  | `first_available` | +15.45 ± 0.25 min (9.1 → 24.6) | −0.3 ± 0.1 /h | c_a full 44.5% of the time, mill_b idle +5.8 pp |
  | `round_robin` | +1.12 ± 0.18 min | −0.2 ± 0.1 /h | ignores the failing mill_b, so its queue grows |

  Common random numbers help less here (2.1× vs 5.6× for the buffer change): a different routing rule sends the same arriving part to a different mill, so the two scenarios drift apart more.
- **Display:** differences of percentages are shown in percentage points (pp). Small nonzero differences get extra decimals instead of showing as `+0.00` next to "higher".

## Scenario files (implemented 2026-10-09)

A scenario is a base model plus a list of changes, instead of a full copy:

```yaml
format: outliers-sim-scenario/0.1
name: two-cells-first-available
base: two-cells.yaml            # relative to the scenario file
changes:
  sources.arrivals.output: { rule: first_available }
```

- **Paths:** each change replaces the value at a dotted path (`conveyors.c2.length`, list items by index: `servers.mill.failures.0.downtime`). The last segment can be a new key of an existing map (e.g. `servers.lathe.capacity` when the base didn't set it). `format`, `name` and `description` are set at the top of the scenario, not as changes. Removing objects isn't supported; topology changes are still full copies.
- **Path errors** say what exists ("`servers` has no `mil_b` (it has: mill_a, mill_b, inspect)").
- **Loading:** the base must load on its own first; its errors are reported in the base file. The changes are then applied to a generic YAML tree, the result is written out as YAML with every line tagged with its dotted path, and loaded like any model. Errors are mapped back to the change that caused them and reported at that change's line in the scenario file, with the usual message ("with this change: unknown variant `round_robn`, expected one of ...").
- **A scenario is exactly equivalent to the full copy it replaces:** a test checks the loaded models are identical, and the `compare` results for the examples are unchanged to the last digit.
- **Layouts:** a scenario uses its base model's layout file.
- **The examples' scenario copies are now scenario files:** `conveyor-line-longer-c2.yaml`, `two-cells-first-available.yaml` and `two-cells-round-robin.yaml`, each about 8 lines.
- **The format is meant to be the web UI's save format and the API's payload:** a change set is just a map of paths to values.

## Web application and API (decided 2026-10-09; `serve`, API and web UI implemented)

The target deployment: IT hosts the simulator on a server, and users open it in a browser to configure scenarios, press play, and get a report and animation.

- **One binary:** `outliers-sim serve --models <dir> --port <n>`. It serves the web UI and runs simulations on the server, natively, on all cores. Why the server and not WebAssembly in the browser: full performance, models and scenarios shared by the team, and thin clients (tablets work).
- **No build step:** the web UI is plain HTML/JS compiled into the binary, like `report.html`. No npm, no CDN, works on intranets without internet.
- **HTTP library: `axum`/`tokio`.** It's build-time weight only; the shipped binary is still a single static file with no runtime dependencies.
- **Job queue:** concurrent runs wait their turn instead of fighting over cores; progress is streamed to the browser.
- **Storage:** no database. Models and scenarios are YAML files in a folder, which IT can back up or put in git.
- **Security:** HTTPS and authentication come from IT's reverse proxy, not built in for v1.
- **The web UI uses only the public, documented HTTP API**, so anything a user can click, a programmer can script (Python, R, curl). An OpenAPI description will be published. The CLI and its file formats stay the batch/CI interface. A Python package wrapping the engine in-process is a later option.
- **Animation:** a plain 2D top-down canvas replay (a port of `viewer/scripts/replay.gd`, which is tested against the engine) is the default: instant, about 30 KB, works on tablets. The UI shows a **"3D" button as a placeholder** for a future Godot web export of the viewer, kept so it isn't forgotten. That export is roughly 35–40 MB of WebAssembly (8–10 MB compressed, to be measured), cached by the browser and loaded only on demand. The user judged that acceptable compared with existing DES software, but 2D comes first.
- **`serve` as built:** documented in `docs/api.md`.
  - **Endpoints:** list, read, check and save models/scenarios; queue, poll and fetch runs.
  - **Models:** `GET /models/{file}` returns the model as a tree with a scenario's changes applied. Change paths address that tree, which is what forms read and write. Base models are never overwritten through the API; only scenarios are saved.
  - **Validation errors** name the change path at fault (`"change": "conveyors.c_a.speed"`), so the UI can mark the field.
  - **Runs** go through the same `runner` module as `outliers-sim run`, so results are identical. A single worker thread runs one job at a time on all cores; others wait as `queued`. Progress counts finished replications. Unsaved scenarios are stored with their results as `scenario.yaml`. The run list is in memory; result folders persist.
  - **Security:** listens on `127.0.0.1` unless `--host` says otherwise. Model names are plain file names (no paths), and run files come from a fixed list, so requests can't reach outside the two folders. Responses are gzip-compressed; the event log goes from 7.3 MB to 0.8 MB.
  - **Dependencies added:** `axum`, `tokio`, `tower-http` (gzip). 109 crates in the CLI's build tree, still one static binary.
  - **Tested** through the router (6 tests: listing, detail, check, save/refuse, runs of files and unsaved scenarios, path traversal) and by hand with `curl` and the Python sweep example in `docs/api.md` against the real server.
- **Web UI as built** (`crates/cli/src/web/`, `index.html` + `app.js`, about 900 lines, no framework):
  - **Opening a model** shows a 2D diagram (from the layout, or the same automatic layout as the viewer) and a property panel. Click an object or conveyor to edit it; click empty space for the experiment settings.
  - **Forms by object type:**
    - source: interarrival, when blocked, routing rule and weights;
    - server: capacity, process time, input rule and priority order, routing rule, failures (add, edit, remove);
    - conveyor: length, speed, spacing;
    - experiment: replications, warm-up, run length, seed.
  - **Edits become scenario changes** at the same paths the API uses. Setting a value back to the base's removes the change. Changed fields and objects are marked, with a reset link.
  - **Validation as you type:** every edit is checked through `POST /check` (debounced). Errors appear under the field they belong to, and the object is outlined in red in the diagram.
  - **Save as scenario** writes an 8-line scenario file through `PUT /models/{file}`. **Run** queues the file (if unchanged) or the unsaved scenario, then shows progress (replications done) and opens the results.
  - **Results:** the report (the same self-contained `report.html`, in a frame), the **2D animation**, the **"3D" placeholder button** (explains that the Godot web view is planned and loads on demand), and download links.

## Packaging and deployment (implemented 2026-10-09)

- **Static binary** for `x86_64-unknown-linux-musl`, 5.7 MB stripped (release profile: `strip`, thin LTO). Release archives (binary, examples, docs, deploy files, SHA-256) are 2.2 MB.
- **Docker image:** about 8 MB. The binary is built on Alpine (musl, static), and the final image is `scratch` with only the binary and `/data/{models,runs}` (examples preloaded), running as uid 65532. Tested here: health, model list, a run through the API, results kept in the volume, and `docker stop` in 0.25 s (clean shutdown on SIGTERM). A CI job builds the image and checks the container answers and runs.
- **The server handles SIGTERM** (systemd, Docker) as well as Ctrl+C, and has `GET /api/v1/health` for monitoring.
- **`deploy/outliers-sim.service`:** a dedicated system user, `StateDirectory`, listening on localhost, systemd sandboxing. `systemd-analyze verify` passes; not installed for real here (that needs root).
- **`deploy/nginx.conf`:** HTTPS plus basic auth in front, and a sub-path variant (the UI uses relative URLs). `nginx -t` passes.
- **`docs/deploy.md`:** install (binary + systemd, or Docker), security, sizing, backups, cleanup, upgrades, logs.
- **Release workflow** (`.github/workflows/release.yml`): on a `v*` tag, it builds the static binary archive and creates a GitHub release, and pushes the image to `ghcr.io/<owner>/outliers-sim`. Not run yet; it runs only when a version is tagged. Its packaging step was reproduced locally.
- **Performance fix found while packaging:** the first static build was **24× slower** than the glibc one, because musl's allocator struggles with the engine's per-event temporary allocations (conveyor position lists, routing helper lists). Those are now allocation-free: lazy position iterators, in-place updates, index loops. Static is now within about 35% of glibc (0.19 s vs 0.14 s for 120 replications of the conveyor line), and the glibc build itself got about 25% faster. Results are **byte-identical** before and after (summary, per-replication data and full event logs of every example compared).

## Three audiences, three interfaces (decided and started 2026-10-09)

The product has three kinds of users, with completely separate interfaces over one API:

1. **The developer** hosts the app, uses the API, and builds integrations, automations and webhooks, maybe even their own UI.
2. **The engineer** knows the domain and the math but isn't necessarily tech-savvy. They build the model in the UI (`/modeling`), and git versions it.
3. **The manager** wants answers like "how much does throughput go up with a faster machine?". They open a project, build scenarios from the parameters the engineer exposes, and compare reports (`/simulation`).

Decisions so far:

- **No access control for now:** just separate pages (`/` lists the projects, `/modeling` and `/simulation` open one). Roles come later, likely through the reverse proxy.
- **Git stays local:** one repository per project, no remote.
- **No review step:** the engineer publishes when they want; in practice they model alone.
- **Projects** (`<data>/projects/<id>/`): `project.yaml` (format `outliers-sim-project/0.1`, name, description, `model:` file), the model and its `*.layout.yaml`. Git is run as a command with a fixed identity and no user config (hooks, signing). The engineer never sees it.
- **Engineer flow:** edits are pending changes in the browser, checked as they type, exactly like scenario changes. **Save version** applies them, rewrites the model file and commits with the engineer's message. **Publish** tags the last saved version `vN`. A published version's description defaults to that commit's message, so managers see what changed instead of "Version 2". Publishing needs a valid model and refuses an already-published or dirty working copy.
- **Saving rewrites the model file in standard formatting** (`outliers_sim_model::to_yaml`: block-style maps and lists of maps, flow lists of plain values, quotes only when needed). Comments in hand-written files are lost on the first save from the builder. A test checks the writer round-trips every example to the identical model. Keeping formatting would need a YAML writer that edits in place; not worth it yet.
- **Managers only see published versions,** read straight from git at their tag (`git show vN:file`). Later saves never change what they're looking at.
- **Runs** take a project, a version (absent for the working copy, `latest`, `vN`) and optional changes. Each run keeps the exact model text it ran (`model.yaml`), so results stay traceable even for unsaved edits.
- **The API changed shape** (projects instead of a flat models folder); `docs/api.md` is rewritten. `serve --data <dir>` replaces `--models`/`--runs`. An empty data folder gets the example projects, saved and published as v1.
- **Docker image:** now Alpine plus git, about 41 MB (was 8 MB on `scratch`). Replacing the git command with a pure-Rust git library would shrink it again, at the cost of a big dependency; not done.
- **Next (planned 2026-10-10, in this order):** manager comparisons; then exposing decisions from the builder; then drawing models in the builder (place, connect, delete and rename objects; conveyor length follows the drawing by default; whole-model saves including the layout; distribution pickers; undo).

## Paced lines (implemented 2026-10-21, issue #33)

- **`lines: { front: { stations: [frame, drum], takt: "2.5 min" } }`**: the stations (servers, capacity 1, no batches, in one line only) release finished parts only when the line moves. A takt event checks the stations: if all are done, the line moves; if not, it waits for the last, moves when it finishes, and the next takt counts from then ("a station that isn't done stops the line"). Moving releases the stations last-first, so each frees its place before the one before hands over.
- **Built on the existing gates**, not a new kind of object: a station's blocked parts simply wait for the line, so routing, resources, failures and shifts work as before. A failure pauses its station's part, which stops the line until repaired.
- **Results:** moves, stops, stopped (share of the line's working time, all stations on shift: off shift a line is off, not stopped) and stops caused by each station.
- **Not done:** units continuing incomplete to be finished off-line, and moving the line while a station is still working.
- The assembly line has a decision "How frame and drum move machines on": buffered (as before) or paced every 2.5 minutes with room for one between them. Paced, jams at the drum stop the frame too: lead time 64 minutes instead of 47 and slightly lower throughput, which is the comparison the issue asked for.
- Scenario changes may now also create `queues`, `transports`, `vehicles`, `lines` and `parts` sections, so a decision can turn a line paced.

## Vehicles (implemented 2026-10-21, issue #31)

- **Vehicles carry parts along transports**: `vehicles:` (count, speed, load and unload times, a home object) and `transports:` (from, to, by, distance, optional capacity). A transport is a connection like a conveyor or queue, so routing, merging and blocking work unchanged; the receiving object takes delivered parts like from a queue.
- **Dispatching:** the part that has waited longest gets the nearest idle vehicle. A vehicle that delivers stays where it is (no return home yet).
- **Distances are in the model, not taken from the layout**: the engine never reads layouts, and a run mustn't change because someone moved a box on the drawing. An empty trip uses the distance of a transport between the two places, or the requested transport's own distance. A path network (aisles, one-way lanes, congestion) can come later.
- **Each vehicle is a small state machine** (idle, to pickup, loading, carrying, unloading), stepped by one event type. Results: transport *waiting for pickup*; fleet *busy*, *empty travel*, *trips*. The event log has `vehicle_trip` and `delivered`; the web animation draws vehicles moving with their load (the Godot viewer handles the events but doesn't draw vehicles yet).
- **Not yet:** vehicle schedules, failures and charging; returning home when idle.
- Tested with exact answers: one vehicle, a part every 10 minutes, 60 m at 1 m/s and 10 s to load and unload: every part after the first takes exactly 140 s and the vehicle is busy 140/600 of the time, 60/600 empty.
- The warehouse's forklifts are a fleet carrying pallets 60 m from the dock to the racks, instead of a resource held for a fixed "trip time".

## Changeovers (implemented 2026-10-21, issue #32)

- **`changeover:` on a server**, one time for any change of part type, or `from->to: time` per change (others take none). Each slot remembers the type it last started, so parallel stations change over independently; a batch changes over once.
- **The setup is added to the processing time**, from the server's own `changeover` stream. It holds the slot and the resource units like processing does, pauses with failures and shifts, and counts as busy. Servers report *changeovers* and *changeover* (share of working time setting up).
- **Not done here:** sequencing at the release (batching similar models to save changeovers). Sources draw a random mix; a release that alternates or batches types can come with a scheduled release.
- The assembly line's packing station changes over for the other model (1.5 minutes), 25% of its time; a decision tries quicker changeovers.

## Finishing the work in hand after a shift (implemented 2026-10-21, issue #30)

- **`finish_work: true` on a schedule**: servers and resources on it don't stop at the end of a shift while there's work for them; they stop when there's none left. Sources ignore it: arrivals stop on time.
- **"Work for them"** is parts in the server, parts on its incoming conveyors and queues, and parts that can still come: an upstream server that's still working on something, or a source still on shift. Without looking upstream, the tellers would go home while the kiosk still had a customer for them. A resource has work while a server that needs it has.
- **Overtime counts as working time** (it's not off shift), and is reported as *overtime per week* for servers and resources on such a schedule.
- **Caveat:** a server whose resource stops on time (a schedule without `finish_work`) can't finish; it stays in overtime with nothing to do until the next shift. Put both on the same schedule.
- **Not done here: terminating simulations** (each replication one day: open, close, drain, results per day). Weekly schedules with `finish_work` cover the bank; a day-per-replication mode can come later if a model needs it.
- The bank's staff hours are now its real ones (09:45–16:00, finishing up), instead of running to 17:00 so customers weren't stuck overnight. Its Simulation page shows teller overtime (about 17 minutes a week).

## Which part's clock an assembly keeps (implemented 2026-10-21, issue #29)

- **`keeps_clock_of: order`** on an assembly server: the new part's time in system counts from its earliest component of that type, instead of its earliest component of any type. Without it nothing changes.
- **Why:** when one component is the customer's request and the others are stock, the earliest component is usually stock that waited for days, so "time in system" measured the stock's age, not the order's lead time. The warehouse read 38 hours; timed from the order it's 12 minutes, which is what its Simulation page now shows as "Order lead time".
- Kept as one named component rather than per-component times, which can come later if someone needs "how long did the order wait for stock" as its own number (the backlog queue's waiting time already says that in the warehouse).

## Stock and restocking (implemented 2026-10-21, issue #28)

- **A restocking source keeps a queue stocked**: `restocks: racks`, `reorder_point`, `order` (a fixed quantity, ordered as many times as it takes to get above the reorder point: (s, Q)) or `order_up_to` ((s, S)), a `lead_time`, and optionally `review_every` for periodic review instead of continuous. Deliveries come after the lead time all at once (a group arrival), and wait for the next shift if the source has a schedule.
- **Why on a source, not on the queue:** what a supplier does (order, wait, deliver) is where parts come from; the queue is just where the stock is. The source's deliveries still travel the model (dock, unloading, putaway) before they're stock.
- **The stock position counts the pipeline:** the queue's contents, plus everything the source delivered that hasn't reached the queue, plus what's on order. Without the pipeline, a source would reorder while pallets are still on the dock. It's counted as the queue's starting stock + parts the source created + on order − parts that left the queue, over the whole run (not reset after the warm-up).
- **`starts_with` on a queue**: parts at time 0, a number when one part type travels on the queue, `{ type: n }` otherwise. A new `stocked` event puts them in the animation.
- **Results:** orders placed and mean on order for the source; *empty* (time out of stock) for queues that are stocked. Fill rates on the demand side come from the waiting queue's service level (#24).
- Checked: a restocking source's parts must be able to reach its queue; order-up-to levels must be above the reorder point.
- **The warehouse template now restocks**: a truck of 25 pallets is ordered when the racks (with what's on the dock and on order) fall to 250, delivered 18–30 hours later on the morning shift. The racks never run out and orders wait seconds; the reorder point is a decision on the Simulation page, with "Pallets in the racks" and "Time the racks are empty" as the trade-off. Before, independent supply and demand flows drifted, and some replications ran out for days.

## Arrivals in groups, and splitting (implemented 2026-10-21, issue #27)

- **`group: 20` or `group: { min: 20, max: 30 }` on a source:** each arrival brings that many parts at once. They get on in order; the first that can't makes the rest wait behind it (or, with `drop`, each that can't is lost), and the next arrival time starts when the last has got on, as for single parts. All of a group arrive at the same instant: a queue with room for one takes one part before the next object can take anything, so the others are lost or wait. Pulling at once instead would have objects calling into each other mid-update; the instant rule is simpler and documented.
- **`splits_into: { carton: 10 }` on a server:** each finished part becomes that many parts of another type, which leave one by one from its slot (the slot stays blocked until the last has gone). They keep the original's arrival time, so a carton's time in system counts from when its pallet arrived. The original counts as consumed; a new `split` total keeps the conservation check (created + assembled + split = exited + lost + consumed + in system).
- **Counts** are a whole number or a uniform range `{ min, max }`, drawn from the object's own `group` or `split` stream. Variable kit sizes (an order of 1 to 5 cartons) are left for later.
- The event log has a `split` event; the web and Godot animations show split parts leaving the server.
- **The warehouse template is now trucks of 20–30 pallets**: forklifts put pallets away into the racks (one pallet a trip, so the "8 cartons a trip" batch is gone), a station breaks pallets into 10 cartons onto the pick shelves, and only when the shelves have room, so they restock themselves. Supply and demand balance only on average, so some replications run out of cartons; restocking by stock level is issue #28.

## Arrivals by time of day (implemented 2026-10-21, issue #26)

- **`arrivals_per_hour: { "10:00-12:00": 40, "12:00-14:00": 70 }`** on a source, instead of `interarrival`: a Poisson process whose rate changes with the time of day, the same every day, zero outside the periods. Periods are written like shifts and may run past midnight; they can't overlap.
- **Rates, not times between arrivals**, because that's how arrivals are counted and planned ("70 customers an hour at lunch"), and because a changing rate is a Poisson process with an exact, standard sampling method.
- **Thinning** (Lewis and Shedler): candidate arrivals at the highest rate from the source's interarrival stream, each kept with probability rate(t)/highest rate, drawn from a new `thinning` stream. Sources with `interarrival` use their streams exactly as before, so their results don't change.
- **With a schedule**, the source creates parts only while the schedule is on and the rate is above zero; at a shift's start the next arrival is drawn from the rate rather than coming at once.
- **One profile for every day.** Different profiles per weekday can come later; a schedule already turns days on and off.
- The bank template has a lunch peak (40, 70 and 45 an hour), which makes the tellers decision matter: at 70 an hour three tellers are nearly saturated. Its "longer hours" option spreads a similar day over 09:00-17:00. The Modeling page edits the periods in a small table and says how many arrive a day.
- Tested: counts per period match the rates (5 replications × 28 days, within 4 standard deviations), nothing arrives outside the periods or off schedule, and the errors.

## Words for what flows (implemented 2026-10-21, issue #25)

- **`parts: { one: customer, many: customers }`** at the top of a model. The Modeling page ("Customer types", "Where customers come from"), the report ("of 15 customers on average", "mean customers") and `validate` ("holds 15 customers") use it. Without it, "part"/"parts".
- **Both forms are written out**, not derived: English plurals aren't regular enough (box/boxes, person/people).
- **Measure names don't change** (`mean parts` in summary.json and in `results:`), so result files, project files and scripts are the same whatever a model calls its parts; only what people read changes. The report shows measure names in the model's words.
- The Modeling page sets it in Model settings, next to the part types. The bank template uses customers.

## Waiting time and service levels (implemented 2026-10-21, issue #24)

- **Queues report the wait people talk about:** the mean, the 90th percentile, the longest wait, and the mean per part type when several types wait in the same queue (which types travel on each connection is now worked out with the other "types at" checks).
- **Service level: `target_wait` on a queue** adds *within target wait*, the share of parts that waited at most that long. It's on the queue, in the model, rather than a threshold chosen on the Simulation page, because every measure is computed per replication when the model runs; the target is part of what the model measures. Counted exactly by the engine.
- **Percentiles from a histogram**, not from every observation: bins 1% apart from 1 ms (no wait at all counted exactly), so memory doesn't grow with the run, and a percentile is within about 0.5% of the exact one. Only queues keep one.
- Validated against M/M/1: the share waiting at most 5 minutes (1 − ρe^−(μ−λ)t) and the 90th percentile (ln(ρ/0.1)/(μ−λ)).
- The bank template sets targets of 5 minutes for tellers and 15 for advisors, and its Simulation page shows "Served by a teller within 5 minutes".

## Results over working time (implemented 2026-10-21, issue #23)

- **States are shares of working time.** For a server with a schedule, busy, blocked, failed and idle (and waiting for resources) are shares of its shifts, and add up to 1 without off shift; off shift is still reported, as the share of the whole week. A resource's busy is the share of its units in use while on shift. Before, everything was a share of the calendar week: the bank's tellers read 12.5% busy instead of about 54% of their shift. Servers and resources without a schedule are unchanged.
- **`outputs.throughput_per`: hour, day, week, or a schedule's name.** One setting for every throughput in the model (sinks, per type, queues, conveyors), so files, the report and the Simulation page agree. A schedule's name means per hour of that schedule's working time within the measured period (computed exactly, so run lengths needn't be whole weeks). New units: `parts/day`, `parts/week`, `parts/working h`.
- Why one model-wide setting rather than per result: throughput is the same kind of number everywhere in a model, and mixing units between a sink and a conveyor would be confusing. Results on the Simulation page follow it.
- The assembly line, bike assembly and warehouse templates count throughput per working hour of their shifts. The Modeling page sets it under Model settings ("Count throughput per"), and renaming or deleting a schedule keeps it right.

## Queues (implemented 2026-10-21, issue #22)

- **A queue is a connection, like a conveyor, with no travel.** `queues: { line: { from: kiosk, to: tellers, capacity: 15 } }`. Parts are at its end as soon as they get on and leave first in, first out. Without `capacity`, there's no limit, which also covers "a link without a conveyor".
- **Why a connection and not an object:** in this model language parts always wait *between* objects, at the end of what feeds the next one. Making the queue that connection keeps every existing rule (blocking, `when_blocked`, routing and merging by name, priorities) working unchanged, and needs no new "link" concept.
- **In the engine it's a conveyor with no length and no spacing**, so the conveyor code runs it as is: queues and conveyors share `Spec::conveyors` (queues after conveyors), with a kind. Validated against queueing theory: M/M/1 waiting time and M/M/1/K losses with queues (no transit time to subtract).
- **Drawn straight between their objects**, dashed, with the capacity (`teller_line · 15`, `∞` for none). They aren't in layout files, so dragging an object can't change the model. The warehouse's 1,000 m storage conveyor, which a drag would have shrunk to 23 cartons, is now a queue of 2,000. Two queues between the same objects in opposite directions are drawn side by side.
- **Every connection now records the time parts spend on it.** For queues it's reported as *waiting time*, next to mean and most parts waiting, time full and throughput. The report has a Queues section.
- The bank and warehouse templates use queues: the bank's lines (with "Wait for a teller" as a result) and the warehouse's storage and order backlog.
- The Modeling page connects objects with "→ Conveyor" or "→ Queue"; a queue's panel has its capacity (empty for no limit).

## Templates, and examples from different industries (implemented 2026-10-21)

Three examples, one per kind of system, built only with what the model language has today, to find what's missing:

- **Washing machine assembly line** (`assembly-line`): two models on six stations, two shifts, a jamming drum station, a final test with 8% rework by one technician.
- **Bank branch** (`bank-branch`): customers take a ticket and wait for tellers (quick) or account advisors (advice); when a line is full, newcomers leave. Customers are "parts" and the lines are conveyors they walk along.

## Managing projects (implemented 2026-10-21)

- **Rename and describe** from the project list (the ⋯ menu on a card). The name and description live in `project.yaml`, so a change is saved as a version ("Renamed to …"), like any other edit. The id never changes: it's the folder name, the address in links, and the key for scenarios. The name and description shown are always the current ones, even when looking at an older published version: they describe the project, not a version.
- **Archive, then delete.** Archiving moves the project to `<data>/projects/.archive/<id>/` with everything in it; it can be undone right away ("Undo") or later from "Show archived projects". Only archived projects can be deleted, which removes the folder and the project's scenarios. Two steps, so nothing is lost to one misclick. An archived project keeps its id taken, so a new project can't inherit its scenarios.
- **Examples only for a new data folder.** They used to be created whenever the project list was empty, so deleting them all brought them back on the next restart. (Since then, new data folders get no projects at all: see Templates.)

## Animation needs an event log (fixed 2026-10-10)

- **The bug:** a model without `outputs.event_log: jsonl` records nothing to replay. The Animation tab used to fall back silently to the report, so on the Simulation page the button seemed broken. Projects from the new-project template had no event log.
- **The fix:**

  - The Modeling page's model settings have a "Record an animation" switch.
  - The Animation tab explains how to turn recording on when a run has nothing to animate.
  - A new run on the Modeling page opens on its report, while reopening an old run keeps the last tab.

## Batches and assembly (implemented 2026-10-10)

- **Server kinds:** a server processes one part at a time (as before), a **batch** (`batch: N`), or an **assembly** (`assembles: { type: count }` and `makes: type`). Batch and assemble together is an error. Both kinds take one process time, not one per type.
- **Collecting is separate from slots.** A batch server takes waiting parts (by its input rule) into the batch until it's full. An assembly server takes a waiting part only if the kit still needs its type, so others stay on their conveyor and can block it. Collection needs the server up, not a free slot. The batch or kit starts when it's complete and there are enough free slots and resource units (it joins the resource queue when only units are missing).
- **Batches:**
  - One process time is drawn per batch.
  - One slot is used per part, all finishing together, and parts then leave one by one as usual.
  - Resource units are taken once per batch: the first slot holds them. Each slot now records whether it holds the server's units.
  - Capacity defaults to the batch size and must be a multiple of it.
  - A partial batch waits forever. A timeout to start a partial batch is not done yet.
- **Assembly:** a complete kit is consumed and becomes a new part of the `makes` type, with a new id. Its creation time is the earliest component's, so time in system covers the whole kit. Totals gain `assembled` and `consumed`, and conservation becomes created + assembled = exited + lost + consumed + in system (collected parts count as in the system).
- **Validation follows types through assemblies,** which send out only what they make. An assembly must be reachable by every type in its kit (or no kit would complete). Every type that reaches it must be in its kit (or it would wait forever). This reachability now lives in the engine (`Spec::types_at`), and sinks use it to report per-type measures only for types that can arrive, and only when more than one can.
- **Event log:** `collected` (off the conveyor into a batch or kit), `consumed` (a component used up) and `assembled` (a new part, with its type, which then `started_process`). Both replays track collected parts at the server and count assembled/consumed parts for "in system". A Godot test fixture covers kits, a batch oven, a resource and a shift.
- **Example:** `examples/bike-assembly.yaml` uses all four features (part types, a fitter resource, two weekday shifts, kits and a batch oven). It's the third example project, with decisions on fitters, a night shift and the oven batch size.
- **Modeling page:** "Works on" on servers (one part at a time, in batches, assembles kits), with the batch size or the kit and what it makes.

## Schedules (implemented 2026-10-10)

- **Format:** `schedules: { name: { shifts: ["06:00-14:00", ...], days: [mon, ...] } }`, weekly. Time 0 is Monday 00:00. Shifts are clock times; one ending at or before its start ends the next day (a night shift). Overlapping and touching periods merge. A Sunday night shift wraps into Monday, and that counts as one shift (no change at the week's boundary). Schedules have their own namespace.
- **Servers off shift behave like failed ones:** processing pauses (always resume, never restart) and continues at the next shift. Nothing is taken in or released, and failure clocks pause, `clock_time` ones too: the machine isn't running. A repair in progress continues. When it ends off shift, paused parts wait for the shift. This reuses the failure machinery, which is already validated.
- **Resources off shift:** no new units are handed out. Units in use stay until their part is done ("the operator finishes the part in hand"). At the shift's start, waiting servers are served first come, first served.
- **Sources off shift:** no arrivals. The first arrival of each shift comes at its start. A shift end cancels the pending arrival through a generation counter, like other stale events. Ties at the same instant follow the event list's FIFO rule: the shift end at 14:00 was scheduled before the 14:00 arrival, so that arrival doesn't happen.
- **Results:** server and resource *off shift* fractions. A server's states add up to 1 with off shift first (it beats failed). A resource's *busy* stays the share of all its units over all time.
- **Event log:** `shift_ended` / `shift_started` for servers. Both the 2D animation and the Godot viewer show an *off shift* state.
- **Not yet:** breaks inside shifts (write them as two shifts), holidays, a schedule for conveyors, and "finish the part, then stop" at shift end.

## Shared resources (implemented 2026-10-10)

- **`resources: { name: { capacity: N } }`**, with servers saying `needs: { name: units }`. Resources share the object namespace, so a measure's object name is never ambiguous.
- **All at once:** a server starts a part only when it can take every unit it needs at once. It never holds some units while waiting for others, which rules out deadlocks over resources. A need above the resource's capacity is an error ("it could never start").
- **Held while processing,** including while suspended by a failure. Units go back when processing ends, not when the part leaves, so an operator doesn't stand by a blocked machine.
- **One queue, first come first served:** when units come back, every waiting server tries again in the order it started waiting. Servers that still can't start rejoin the queue in the same order. A server joins only when it's up, has a free slot and a part is waiting at its input.
- **Results:** `resource <name>: busy`, the time-weighted share of units in use. `server <name>: waiting for resources`, the share of time it was queued for units. That time is part of *idle*, so the server states still add up to 1. Both are reported with `server_states`.
- **Starting a section with a change:** a change may now create a top-level model section the file doesn't have yet (`resources.operator: { capacity: 1 }` on a model without `resources`). Other unknown top-level names are still reported as typos. Without this, the Modeling page and API scripts couldn't add the first resource.
- **Modeling page:**
  - *Resources* in the model settings (add, rename, remove, units available). "⚑ Make this a decision" works on the number of units, for "hire a second operator".
  - *Needs while processing* on servers.

## Part types (implemented 2026-10-10)

- **Where types come from:** `entities` lists the part types. A source `creates` one type, or a mix with shares adding up to 1. Each arrival's type is drawn from the source's own `type` stream, which is only used for mixes, so single-type models give byte-identical results to before.
- **Process times per type:** `process_time` is one time, or a map type -> time. Routing by type is a new output rule, `by_type`, with `routes: { type: conveyor }`. The part waits for its conveyor.
- **Validation follows the types:** which types can reach each server is computed by following `by_type` routes from the sources. Every type that can arrive needs a process time (when given per type) and a route (with `by_type`). Types that never arrive don't.
- **Results:** with two or more types, each sink also reports `throughput of <type>` and `time in system of <type>`. Measure names became strings for this. Decisions and results can name these measures like any other.
- **Event log:** the header lists `entities`, and `created` events carry `entity`. The 2D animation colors parts by type (six colors, distinct from the server-state colors, with a legend). The Godot viewer ignores both for now.
- **Format detail:** per-type values (`creates`, `process_time`) are read by hand-written deserializers, because positions don't survive untagged choices in the YAML library. Their errors point at the field, not at the entry inside it.
- **Modeling page:**
  - *Part types* in the model settings (add, rename everywhere, remove).
  - A *Creates* field on sources: one type, or "A mix of part types…" with shares.
  - "Different times per part type…" on servers.
  - The `by_type` rule, with a conveyor per type.
- **Model reference:** `docs/models.md` now documents the whole model format.

## Drawing models in the builder (implemented 2026-10-10)

- **Toolbar on the diagram:** + Source, + Server, + Sink, Connect (click one object, then the next), Delete, Undo/Redo (also Ctrl+Z / Ctrl+Shift+Z). Objects are dragged on a 0.5 m grid. The panel renames and deletes the selected object or conveyor.
- **Topology edits are ordinary changes:** adding is a change that sets a whole object, and **`null` removes** a map entry (`"servers.mill": null`), in scenario files and the API alike. Pending edits stay one list of changes, checked live like any other.
- **Deleting tidies up:** deleting an object deletes its conveyors. Deleting a conveyor removes it from its ends' routing weights and priority orders, and drops a routing or merging rule its end no longer needs (fewer than two conveyors).
- **Renaming carries references along:** conveyor ends, routing weights, priority orders, the layout, and the project's decisions and results all follow the new name.
- **Layout:** the builder keeps a full layout (every object and conveyor) and sends it whole (`layout` in `check`, `save` and runs) once anything moved or was added. Positions round to 1 cm. Layouts given as JSON may be in `layout.json`'s shape, with `format` and null fields dropped.
- **Conveyor length follows the drawing by default:**
  - A new conveyor's length is its drawn length.
  - When an object moves, each attached conveyor whose length matched its drawing (within 6 cm) keeps matching.
  - One with a typed length keeps it, and the layout check warns that the drawing differs, as before. No extra flag is stored.
- **Routing:** conveyors are drawn straight, with a Z-bend, or around the top when they go backwards. Hand-drawn paths of untouched conveyors are kept.
- **Distribution picker:** time fields (arrivals, process times, uptime, downtime) choose a distribution by name and fill in its parameters with units. The expression the model stores is shown underneath. Text the picker can't read stays a plain field.
- **New projects** start as a simple line (arrivals, one machine, exit, with a layout) or as a copy of an existing project (`POST /projects` without `from`).
- **Not yet:** editing conveyor bends by hand, snapping objects to each other, copy and paste.

## Decisions, scenarios and plain-language comparisons (implemented 2026-10-10)

- **Wording:** "engineer", "manager" and "developer" describe the roles in these notes only. The product never calls its users that, because the people on each page may have any job. UI and user docs name the pages and what they do: the Modeling page, the Simulation page, decisions, scenarios, the API.

- **The engineer exposes `decisions` and `results` in `project.yaml`,** versioned with the model, so each published version carries its own. A decision is either a set of **options** (each a group of model changes; the first option is the current setup and has none) or a **number** at one model path within `min`/`max` (optional `step`, and `unit` for quantities like `8 m`). Results name a measure (`object` + `measure`) with a plain label and `better: higher | lower` (or nothing). Without `results`, managers read every sink's throughput and time in system.
- **What can't be published:** an option or bound that gives an invalid model; two decisions changing the same path (or one inside the other); a decision touching `experiment` or `outputs` (every scenario must run the same experiment for the pairing to hold); a number path that isn't written in the model, or written in another unit; a result the model doesn't report; and an option the model already matches (it means the first option no longer describes the current setup, e.g. after the engineer changed the routing).
- **Managers' scenarios** are named picks (decision -> option id or number) pinned to the published version they were made on, stored in `<data>/scenarios/<project>.json`, outside the project's git repository: they're managers' working notes, and the engineer's history stays about the model. Picks are checked against that version's decisions and the resulting model must load. Unnamed scenarios are named after their changes ("Inspectors: 2").
- **Comparisons** (`POST /api/v1/comparisons`) run the current setup and each scenario as ordinary runs (so each keeps its report and animation) with the same seed, so replication r of every run sees the same random events (common random numbers). An identical model already run (or queued) with the same replications is reused. Scenarios from different versions can't be compared together.
- **Plain language, computed on the server** so every client says the same thing. Per result: the current and scenario means in the result's unit, then "up/down X% (between A% and B%)", "no clear change (between −A% and +B%)", "the same in every replication", or "can't tell" with one replication; then "better"/"worse" from the result's direction. Shares of time change in *points*. The percentage range is the paired difference's 95% interval divided by the current mean, ignoring the uncertainty of that mean (small with common random numbers).
- **Too small to matter:** a clear change under 1% (or 1 point) is reported as "too small to matter" and isn't judged better or worse, nor picked as the best scenario. Without it, common random numbers made a 0.06% throughput gain the page's headline. The threshold is fixed for now; a per-result setting may come later.
- **Each scenario gets its own 95% interval;** there's no multiple-comparison correction. The page says in one line that with many scenarios a very small change may look clear by chance. At most 12 scenarios per comparison.
- **Engineers edit decisions in the builder** (implemented 2026-10-10), on a *Decisions* tab next to *Model*:
  - "⚑ Make this a decision" under a number field adds a number decision with guessed limits (half to double; integers from 1). If the model doesn't write the value (like a default capacity), its default is written as a model change, because a number decision needs it written. That written default is never swept into an option.
  - "Offer as an option…" turns the pending model changes into an option of an existing or new decision, and puts the model back as it was. Engineers think in edits to the model, so options are made the same way.
  - The tab edits names, explanations, limits and results, and removes options and decisions. A preview shows what managers will see. Everything is checked live (`check` takes pending `decisions` and `results`) and saved in the same commit as model changes (`save` writes `project.yaml` too). Decision and option ids come from their first name and never change after that, so renaming a decision doesn't break managers' scenarios.
  - Saving from the builder rewrites `project.yaml` in standard formatting, losing its comments, as with the model.
- **The `/simulation` page:** what can be changed (with the current values), scenarios (create, edit, delete, select), "Compare with the current setup", then a headline per result with a direction (the best scenario, or "none clearly improves it"), a table (results x scenarios, with value, change, range, and better/worse as an icon and a word, never color alone), the sentences, and each run's report and animation. Projects without decisions keep the old "Run the published model" button.
